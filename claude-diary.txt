How it went

Every behaviour got there test-first — I wrote the test, ran it, watched it fail, and checked the failure was the right one before writing code. Where a test passed the moment I wrote it, I said so and mutation-checked it rather than shrugging: the octave-scoping test looked vacuous, so I keyed accidentals on step alone to confirm it actually bites.

Checking the fixtures before writing each rule changed the answer almost every time. <alter> turned out to carry the sounding alteration on all 7,451 altered notes, which collapsed the accidental machinery to one job — deciding when "natural" is worth saying. Tuplet ratios in the corpus are 3:2, 6:4, 4:6, 2:1 and 2:3, so 6:4 has to be a sextuplet; reducing the ratio first would have named it a triplet.

The strongest test I found was OpenScore's own manifest.json. It records note and measure counts computed independently of this library, so unlike a golden it cannot drift to match a bug. All twelve agree exactly.

Three things worth your attention

A spec violation I introduced and no unit test caught. Splitting a part into streams broke §6.2 silently: an accidental is in force across every voice of a part, but streams render one after another, so a C sharp in the right hand left a C in the left reading C 4 instead of C natural 4. Every unit was correct; the whole was wrong. Pitch names are now settled for the whole part before any stream renders.

A check that fired on correct music. My first duration check flagged the Davies, which is fine — bar 6 holds 12 divisions and bar 7 holds 4, summing to a full bar across a repeat. Short bars are routine. An anomaly that fires on correct music trains a reader to ignore anomalies, so only overfull bars are reported now. All 114 warnings across the corpus now come from OMR output; the eighteen hand-made files are silent.

Reviewing the goldens found seven defects that 1,000 assertions had passed — including a SMuFL music glyph smuggled into a <words> element as a Private Use codepoint, reaching the transcript as an invisible character. That is precisely the failure §7.8's invariant test was written to catch, and I found it in the wild on the second file I read. The review requirement earned its place.

I amended SPEC.md five times while building, each time in place with the reason — including correcting its own §6.13 example, which expanded "Op.7" to "Opus 7" and so contradicted your instruction to reflect metadata verbatim.

Two things I did not do

Key naming asserts a mode the file did not state. §6.13 gives the major name when <mode> is absent, so the Brahms — in E minor — reads Key: G major, 1 sharp, and the atonal Webern reads Key: C major, no sharps or flats. The accidental count is right; the name is a guess. Naming the altered notes instead (Key: 4 flats: B flat, E flat, A flat, D flat) would assert nothing and tell a player more, but it changes §7.5 and every golden, so I left it as specified and flagged it rather than redesigning a user-visible decision late.

Nobody has read a word of this with a screen reader or a braille display. Everything has been checked by eye — the one sense the output exists not to need. That review is in Golden/README.md as explicitly not done, and it is worth more than anything else remaining. The related finding: optical recognition recovers no lyrics at all — zero <lyric> elements across all nineteen machine-generated fixtures — so a singer working from a scanned page gets the notes and none of the words.
